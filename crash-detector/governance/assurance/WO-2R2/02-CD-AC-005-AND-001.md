### THE COUNTERFACTUAL / CONTROL ARM — the same value through the constructor

**Identical value, identical call, identical window. The only variable is whether the

### WHY THIS IS THE PROJECT'S OWN NAMED FAILURE, IN ITS OWN WORDS
`PanelRow.__post_init__` (`witness_resolver.py:107-116`) describes my attack exactly, as
the reason the constructor re-establishes `state`:

> "`state` decides which panel constructor is reached, and it decides it with `==` against
>  the three declared discriminators. `==` is the LEFT operand's to define, so
>  `isinstance(self.state, str)` admitted a subclass that then answered the question
>  itself: **a row whose stored state is UNAVAILABLE — the witness feed is DEAD — compares
>  equal to "AGREES" and renders WITNESS AGREES.**"

The seat identified the failure precisely and closed it **on the value type**. It did not
close it **at the entry point**. `resolve_panel(row, ...)` admits `row` against exactly one
condition — `if row is None` — and then reads `row.as_of_utc`, `row.state` and
`row.measures` off whatever it was handed.

### THIS REFUTES THE NARROWED INVARIANT — the repair that increment 3 made for CD-PL-F76
`staleness.py:110-124` states, as the invariant of record:

> "WHAT THE CLOSURE ACTUALLY HOLDS: **no method of `type(value)` executes during** … **the
>  selection of a panel constructor from a stored state** … because every one of those
>  operates on a value of exact base type that `crash_detector.own_terms` constructed…
>  **WHAT STILL EXECUTES, AND IT IS EXACTLY ONE THING: `tzinfo.utcoffset`.**"

`LyingState.__eq__` is a method of `type(row.state)`, it executes during the selection of a
panel constructor from a stored state, and it *decides* that selection. **"EXACTLY ONE
THING" is false; there are at least two.** The premise "operates on a value of exact base
type that own_terms constructed" holds only if the row is a `PanelRow`, and nothing
requires that.

**This is the same defect shape, one level up, as the one increment 3 was dispatched to
repair.** CD-PL-F76 said the claim was wider than the closure. The narrowed claim is
STILL wider than the closure.

## FINDING ASR3-F05 — **HIGH** — CD-AC-001 **and** CD-AC-005. `evaluate()` never admits its
## `ConfigSnapshot`, so a caller supplies the staleness window and a TEN-YEAR-OLD
## observation renders as a number.

arm: `arms/ASR3-005-DE.out`

### MEASURED
```
observation age  : 3650 days
declared window  : 600 s   (but the supplied window's covers() returns True for every age)
equity reading   : Value
monetary reading : Value
*** A TEN-YEAR-OLD OBSERVATION PRODUCED A NUMBER: 0.9 ***
```

`evaluate(observations, config_snapshot, now_utc)` is public API. It never admits
`config_snapshot`, and calls `config_snapshot.window()` — so the object that decides
"is this observation fresh enough to use" is supplied by the caller. `ConfigSnapshot`'s own
admission (`StalenessWindow`, the ceiling, the exact-type checks) is real and I confirmed
it; it is simply **not required of `evaluate`'s argument**.

This is CD-AC-001's proposition directly — *"Missing or stale input never renders as
calm"* — reached with **no source edit**, from public API, against an unmodified tree.

### THE PATTERN — this is an inconsistency, not a declared limit
The codebase enforces exact type at **20 sites**, including precisely this shape one level
in:

```
engine/config.py:155     if any(type(spec) is not DialSpec for spec in self.dial_specs)
engine/config.py:179     if type(registry) is not SourceRegistry
source_registry.py:192   if type(source) is not SourceRecord
witness/panel.py:117     if type(self.freshness) is not FreshnessEvidence
```

The idiom is understood and deliberately applied throughout. It is absent at exactly the
**two public entry points of the two judgement paths** — `resolve_panel(row=…)` and
`evaluate(config_snapshot=…)`. Nothing declares that absence.
